**** 22.7.2 Extracting Bundled Dependencies [[#Extracting-Bundled-Dependencies-1][¶]]
:PROPERTIES:
:CUSTOM_ID: Extracting-Bundled-Dependencies-1
:CLASS: subsection
:END:
In Guix every package is supposed to be fully built from source (see [[id:guix--Bootstrapping][Bootstrapping]]). This is at the heart of the security and user freedom guarantees provided by the distribution, and it is what allows Guix to correctly reason about the package graph, to apply transversal changes (say, a security update on a single library) and have them propagate to every dependent package.

Some projects have the habit of distributing the source code of their dependencies inside their release tarball or version controlled source tree. This practice is called /bundling/ and the dependencies shipped this way are called /bundled dependencies/ or in some cases /vendored dependencies/. Common manifestations are a =vendor/= directory in Go projects, a checked in =node_modules/= for JavaScript, a populated =.cargo/vendor/= for Rust, or copies of small C libraries shipped inside another project's tree.

Bundling dependencies conflicts with several Guix invariants:

- When a change must be made in a library---e.g., applying a security fix or removing pre-generated code---that change would need to be repeated in every single package that bundles it.
- Guix mainline ships only free software: bundled trees frequently contain minified blobs whose preferred form for modification is missing (see [[id:guix--Software-Freedom][Software Freedom]]).
- Duplicated source code inflates the closure size and makes =guix size= (see [[id:guix--Invoking-guix-size][Invoking =guix size=]]) and =guix graph= (see [[id:guix--Invoking-guix-graph][Invoking =guix graph=]]) less useful as auditing tools.

For these reasons, we do our best to remove bundled dependencies before submitting a package.

**** Removing Bundled Code [[#Removing-Bundled-Code][¶]]
:PROPERTIES:
:CUSTOM_ID: Removing-Bundled-Code
:CLASS: subsubheading
:END:
Bundled dependencies should be removed in the package's =origin= record, typically using a snippet or a patch, so that the source returned by =guix build --source= corresponds to truly free, unbundled sources (see [[id:guix--Snippets-versus-Phases][Snippets versus Phases]]). When the removal is more involved, for example because it requires regenerating build files or rewriting import paths, it is acceptable to do it in a build phase instead.

Once the bundled tree is gone, the package must be built against existing Guix packages of the same dependencies. When such packages do not yet exist, they must be added.

**** Exceptions [[#Exceptions][¶]]
:PROPERTIES:
:CUSTOM_ID: Exceptions
:CLASS: subsubheading
:END:
Removing bundled code is the rule, but in case a bundled dependency has been changed up to the point that it isn't possible to build a package with the unbundled version of the dependency, it can be considered as part of the source tree it lives in. In general we don't care about upstream's reason for bundling, only the practicality of the unbundling job.
