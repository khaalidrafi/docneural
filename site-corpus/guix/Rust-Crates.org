**** 22.7.13 Rust Crates [[#Rust-Crates-1][¶]]
:PROPERTIES:
:CUSTOM_ID: Rust-Crates-1
:CLASS: subsection
:END:
Rust applications (binary crates) and libraries (library crates) are packaged separately. We put our main efforts into applications and only package libraries as sources, utilizing automation with a manual focus on unbundling vendored dependencies.

Rust applications are treated like any other package and named using the lowercase upstream name. When using the Cargo build system (see [[id:guix--Build-Systems][=cargo-build-system=]]), Rust applications should have the =#:install-source?= parameter set to =#f=, as this parameter only makes sense for libraries. When the package source is a Cargo workspace, =#:cargo-install-paths= must be set to enable relevant support.

Rust libraries are hidden from the user interface and managed in two modules:

- =(gnu packages rust-crates)= :: Source definitions imported from Rust packages' =Cargo.lock= via the =crate= importer (see [[id:guix--Invoking-guix-import][Invoking =guix import=]]).

  Imported definitions must be checked and have vendored dependencies unbundled before being contributed to Guix.

- =(gnu packages rust-sources)= :: More complex definitions that need to be full packages. This includes Rust libraries requiring external inputs to unbundle and Cargo workspaces.

  These libraries should have the =#:skip-build?= parameter set to =#t=. For Cargo workspaces, =#:cargo-package-crates= must be set.

  Since they are added manually, they follow the usual naming convention for Guix packages (see [[id:guix--Package-Naming][Package Naming]]), with a =rust-= prefix.

  In the Rust community it is common for multiple incompatible versions of a package to be used at any given time, so all libraries should have a versioned suffix. The versioned suffix is the left-most non-zero digit (and any leading zeros, of course). This follows the “caret” version scheme intended by Cargo. Examples =rust-clap-2=, =rust-rand-0.6=.

  In practice we often package development snapshots of Rust libraries and can't simply identify them by version. In this case, the complete version information can be turned into a version string via =git-version=, for example =rust-pipewire-0.8.0.fd3d8f7= and =rust-pubgrub-0.3.0.b70cf70=.

When contributing Rust packages, we should have all modifications to these two modules, in the same commit as the package we are contributing.

To avoid merge conflicts with changes from multiple branches, these two modules are maintained by the Rust team (see [[id:guix--Teams][Teams]]).

#+begin_quote
*Warning:* The =(gnu packages rust-crates)= module must not be referenced directly, lest it introduce the risk of cyclic module dependencies (see [[id:guix--Cyclic-Module-Dependencies][Cyclic Module Dependencies]]). Instead, the =cargo-inputs= procedure from the =(guix build-sytem cargo)= module must be used to lookup input lists generated by the lockfile importer.

#+end_quote

- Procedure: *cargo-inputs* =name [#:module ’(gnu packages rust-crates)]= [[#index-cargo_002dinputs][¶]] :: Lookup Cargo inputs for =name= in =module=, return an empty list if unavailable.

  =name= must be consistent with the one used in lockfile importer invocation, usually matching the variable name of the package:

  #+begin_example
  $ guix import -i gnu/packages/rust-crates.scm crate -f /path/to/Cargo.lock name
#+end_example

  =module= must export a public interface =lookup-cargo-inputs=, a template is available in the =etc/teams/rust= directory of Guix source tree.

See [[https://guix.gnu.org/cookbook/en/html_node/Packaging-Rust-Crates.html#Packaging-Rust-Crates][Packaging Rust Crates]] in GNU Guix Cookbook, for packaging workflow.

**** 22.7.13.1 Commit messages [[#Commit-messages][¶]]
:PROPERTIES:
:CUSTOM_ID: commit-messages
:CLASS: subsubsection
:END:
The commit message must have a general brief mention to entry changes in =(gnu packages rust-crates)=. For changes in =(gnu packages rust-sources)=, the commit message must explicitly mention all changes to the packages.

Here are some examples for different situations:

- Adding a new Rust package:

  #+begin_example
  gnu: Add catppuccin-whiskers.

  * gnu/packages/rust-apps.scm (catppuccin-whiskers): New variable.
  * gnu/packages/rust-crates.scm (lookup-cargo-inputs)
  [catppuccin-whiskers]: New entry.
#+end_example

- Updating a simple package:

  #+begin_example
  gnu: watchexec: Update to 2.3.2.

  * gnu/packages/rust-apps.scm (watchexec): Update to 2.3.2.
  * gnu/packages/rust-crates.scm (lookup-cargo-inputs)[watchexec]:
  Update entry.
#+end_example

- Updating a package with sources:

  #+begin_example
  gnu: typst: Update to 0.14.0.

  * gnu/packages/rust-apps.scm (typst): Update to 0.14.0.
  [arguments]<#:rust>: Use rust-1.88.
  * gnu/packages/rust-crates.scm (lookup-cargo-inputs)[typst]: Update
  entry.
  [rust-syntect-5]: Rename to rust-syntect-5.2.
  [rust-syntect-5.3]: New entry.
  * gnu/packages/rust-sources.scm (rust-hypher-0.1): Update to 0.1.6.
  (rust-syntect-5): Rename to rust-syntect-5.2.
  [inputs]: Rename cargo-inputs rust-syntect-5 to rust-syntect-5.2.
  (rust-syntect-5.3): New variable.
#+end_example

**** 22.7.13.2 Resolving merge conflicts in Pull Requests [[#Resolving-merge-conflicts-in-Pull-Requests][¶]]
:PROPERTIES:
:CUSTOM_ID: resolving-merge-conflicts-in-pull-requests
:CLASS: subsubsection
:END:
For Rust crates, the recommended way to solve merge conflicts is to drop all changes to =gnu/packages/rust-crates.scm=, rebase onto the desired branch and run the lockfile importer again, manually adding back all relevant snippets (if any).

See [[https://guix.gnu.org/cookbook/en/html_node/Common-Workflow-for-Resolving-Merge-Conflicts-on-Existing-Pull-Requests.html#Common-Workflow-for-Resolving-Merge-Conflicts-on-Existing-Pull-Requests][Common Workflow for Resolving Merge Conflicts on Existing Pull Requests]] in GNU Guix Cookbook for a suggested workflow on resolving merge conflicts.
